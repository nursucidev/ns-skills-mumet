# NS Review Diff

## Agent role, STOP, and reporting (self-contained)
- **Role:** parent = main agent serving user; subagent = separately delegated worker, including nested workers. Loading this skill never changes role. A subagent **MUST NOT** ask/contact/notify the user, request approval, or invoke user-facing input tools. Report only to the calling agent, which relays upward.
- **Canonical STOP:** If delegated work cannot safely continue because proceeding risks credible major harm or unauthorized production/destructive/data/secrets/cost effects, or needs a consequential decision with no safe authorized default: **STOP the entire delegated task immediately**, including optional work; report evidence (redact secrets), impact, safe options, decision/permission needed and unfinished work **only to caller**; **END**. Never ask/wait for user. A severe finding during an authorized safely continuing read-only review is not automatically a task blocker; finish the review and use `review_verdict: BLOCK` if warranted. A CRITICAL risk rating alone is not a STOP trigger.
- **Report:** only subagents use compact `task_status`, `result`, `evidence/check_results`, `findings`, `decisions_needed`, `remaining`, plus `review_verdict` when reviewing and `release_readiness` only when requested. `task_status` is work progress (`COMPLETED`, `PARTIAL`, `BLOCKED`), separate from check results (`PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `INCONCLUSIVE`, `PRE_EXISTING_FAIL`) and review verdict (`BLOCK`, `FIX`, `NO_FINDINGS`). Parent follows the user's format.

## Ownership
Review a supplied diff and assess review feedback; do not patch files or redo a whole dependency map and risk audit. For a combined change-then-review request, own only the review phase; parent reuses implementation evidence. Use `ns-impact-map` / `ns-risk-review` only for a genuinely unresolved subproblem. This is read-only even if a finding suggests a fix.

## Adaptive fidelity & minimal-complete-change gate (self-contained)
- Discover the real language(s), framework/toolchain **if any**, architecture, conventions, and affected contracts from the project; never assume a stack. No-framework projects use their established style and idiomatic platform/language mechanisms.
- Preserve established project structure, file roles, supported framework integration/lifecycle, behavior and contracts. Prefer existing project code/patterns, then compatible framework/platform facilities, then installed dependencies, then minimal readable custom code; omit unneeded scope and avoid speculative abstractions/dependencies. **Do not bypass a framework or replace project architecture with native/custom code only for brevity or assumed speed.**
- Native/low-level code remains valid when idiomatic, supported within the project mechanism, or justified by an authorized unmet need. A deliberate architecture/data-format deviation requires authorized scope and proportionate compatibility/regression checks. For performance work, confirm a bottleneck and compare results when practical; optimize within conventions first, preserve safety/correctness, and label unmeasured gains unverified. A delegated worker escalates consequential exceptions only to its caller.

## Evidence check: RED–GREEN–REFACTOR (review-only)
- In a review, RED evidence may be a pre-change failing check and GREEN evidence a passing post-change check; REFACTOR must preserve existing behavior and regression checks. Do not require artificial RED for cosmetic, documentation, performance-only, or otherwise untestable work. Missing historical RED is an evidence gap, **not** automatic proof of a code defect.
- Respect read-only boundaries: if RED evidence is useful in a read-only review, inspect existing logs/diffs, or run safe tests **only in a disposable isolated scratch copy**, never mutate original project or protected state. Report actual evidence and uncertainty instead of inventing results. Review framework/project fidelity separately from TDD evidence.

## Procedure
**Read-only boundary:** preserve original workspace/Git state, user data, production and remote systems unchanged. Do not run tools **there** that may write files, caches, logs, databases, or remote state. A requested review permits **safe local disposable sandbox checks without extra approval** only within that request's scope: create the scratch copy **outside the original workspace**, isolate shared caches, symlinks, credentials, volumes, sockets and live network/services, and clean up only the scratch. No production/network writes, spending, destructive work, unknown installers or access beyond task scope is implied. Honor explicit no-execution/no-write restrictions. If effects or isolation are uncertain, do not execute; mark `NOT_RUN` or `BLOCKED` with evidence. Never claim unrun checks passed.
1. Inspect the actual diff and enough nearby code/tests to verify behavior. Never invent a baseline or assume the author's description proves correctness.
2. **Regression review:** reject unsupported native/custom bypasses of existing framework/project patterns, file roles, and lifecycle integration; review performance claims against measurements when practicable. Identify existing behavior and users of changed symbols/contracts; inspect relevant normal, edge/error, and recovery paths in proportion to the diff. Inspect whether tests cover new behavior *and* meaningful prior behavior. Look for changed API semantics, data schemas, permissions, performance, concurrency and platform/version compatibility **where applicable to the diff**; do not force an exhaustive checklist for cosmetic changes. Baseline failures and verification gaps must not be disguised as newly introduced defects. No test result, no claim that a test passed.
3. **Evaluate incoming review feedback when supplied:** read the finding, locate its trigger, verify whether it is true for THIS codebase, check compatibility and existing decisions, and decide `accept | reject with evidence | needs parent decision`. Don't implement reviewer suggestions blindly. In this read-only skill, recommended fixes go to the calling agent if delegated, or to the user if acting as parent; do not edit code.
4. Trace shared contracts using `ns-impact-map` and deeper risks using `ns-risk-review` only if warranted; reading guidance does not require spawning a worker.
5. For each actionable finding: give severity, file/line, triggering scenario, actual consequence, evidence, and concise correction. Distinguish proven defects from uncertainties.
6. Set `review_verdict: BLOCK` for **demonstrated** findings that should block merge/release; `FIX` for actionable non-blocking findings; `NO_FINDINGS` for no actionable findings in inspected scope. **Do not turn missing verification into an invented defect.** If explicitly asked about release/merge readiness, separately state `release_readiness: READY | HOLD | UNDETERMINED | NOT_ASSESSED`: READY needs evidence for all required gates; HOLD if a mandatory check is failed, blocked, or not run, or required approval/mitigation is absent; UNDETERMINED if scope/evidence is insufficient to establish the gates; NOT_ASSESSED if not evaluated. `review_verdict: NO_FINDINGS` may coexist with `release_readiness: HOLD`. A review verdict alone is not safety certification.
7. `task_status` tracks execution, NOT severity. A safely finished review with a critical bug is `task_status: COMPLETED`, `review_verdict: BLOCK`. Use `task_status: BLOCKED` only if required review work cannot proceed safely or within access/authority (for example missing required access). Report scope, regression coverage/evidence, pre-existing failures if known, unrun checks, and remaining verification gaps.
