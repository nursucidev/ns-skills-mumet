# NS Fix Bug — Root Cause & Adaptive Fix Plan

## Agent role, STOP, and reporting (self-contained)
- **Role:** parent = main agent serving user; subagent = separately delegated worker, including nested workers. Loading this skill never changes role. A subagent **MUST NOT** ask/contact/notify the user, request approval, or invoke user-facing input tools. Report only to the calling agent, which relays upward.
- **Canonical STOP:** If delegated work cannot safely continue because proceeding risks credible major harm or unauthorized production/destructive/data/secrets/cost effects, or needs a consequential decision with no safe authorized default: **STOP the entire delegated task immediately**, including optional work; report evidence (redact secrets), impact, safe options, decision/permission needed and unfinished work **only to caller**; **END**. Never ask/wait for user. A severe finding during an authorized safely continuing read-only review is not automatically a task blocker; finish the review and use `review_verdict: BLOCK` if warranted. A CRITICAL risk rating alone is not a STOP trigger.
- **Report:** only subagents use compact `task_status`, `result`, `evidence/check_results`, `findings`, `decisions_needed`, `remaining`, plus `review_verdict` for reviews. `task_status` is work progress (`COMPLETED`, `PARTIAL`, `BLOCKED`), separate from check results (`PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `INCONCLUSIVE`, `PRE_EXISTING_FAIL`) and review verdict (`BLOCK`, `FIX`, `NO_FINDINGS`). Parent follows the user's format.

## Ownership
Primary for defects relative to an existing expected contract. If the user intentionally requests new behavior, use `ns-new-feature` for that distinct phase instead; parent may coordinate combined requests. Consult `ns-impact-map` for unclear consumers or `ns-risk-review` for material risk **only when needed**; avoid repeating whole audits.
- **Investigation-only boundary:** if requested to diagnose, explain root cause, reproduce safely, or propose a fix **without implementation**, do **not** modify application code, configuration, tests, or original project state. Deliver evidence, confidence, minimal proposed fix and checks; stop before changes. A safe local disposable test sandbox may be used only within authorized analysis scope and side-effect boundaries.
- **Concurrent implementation:** edit only resources exclusively assigned by the calling agent; serialize overlapping writers or report the conflict to caller, not user.

## Adaptive fidelity & minimal-complete-change gate (self-contained)
- Discover the real language(s), framework/toolchain **if any**, architecture, conventions, and affected contracts from the project; never assume a stack. No-framework projects use their established style and idiomatic platform/language mechanisms.
- Preserve established project structure, file roles, supported framework integration/lifecycle, behavior and contracts. Prefer existing project code/patterns, then compatible framework/platform facilities, then installed dependencies, then minimal readable custom code; omit unneeded scope and avoid speculative abstractions/dependencies. **Do not bypass a framework or replace project architecture with native/custom code only for brevity or assumed speed.**
- Native/low-level code remains valid when idiomatic, supported within the project mechanism, or justified by an authorized unmet need. A deliberate architecture/data-format deviation requires authorized scope and proportionate compatibility/regression checks. For performance work, confirm a bottleneck and compare results when practical; optimize within conventions first, preserve safety/correctness, and label unmeasured gains unverified. A delegated worker escalates consequential exceptions only to its caller.

## Adaptive RED–GREEN–REFACTOR for authorized fixes (self-contained)
- Use existing project tests/tools regardless of language/framework. For root-cause analysis, identify a falsifiable cause; RED uses a minimal reproducer reflecting the real defect, ideally observed failing before product changes. The check must fail for the expected behavioral reason, not an unrelated setup/environment problem.
- `LIGHT`: test-first optional when disproportional; narrow safe evidence is enough. `STANDARD`: for testable behavior prefer RED before implementation, then GREEN and optionally REFACTOR. `CRITICAL`: use safe, isolated risk-proportionate validation; never alter production or protected data solely to force a failing test.
- **RED:** verify the bug on the unchanged baseline with an existing or newly added targeted regression check when feasible; never manufacture failing code, revert a safe fix, or weaken tests for ceremony.
- **GREEN:** fix the demonstrated cause with the smallest change compatible with project conventions; run reproduction and affected regression checks to PASS.
- **REFACTOR only if beneficial:** improve clarity/avoid duplication/optimize demonstrated bottlenecks; rerun targeted and affected existing regression checks. Never hide contract changes inside cleanup.
- If an executable RED is unavailable, unsafe, or disproportionate, explain why RED is unavailable, record honest `NOT_RUN`/`BLOCKED`/`INCONCLUSIVE` evidence, and verify with a safe proportionate alternative. Diagnosis-only work never edits application code or tests. Performance work can rely on measured before/after baselines without inventing a failing test.

## Procedure
1. **Establish evidence.** Use an existing spec/Feature Walkthrough as the expected-behavior contract if one is provided; there is no mandatory new walkthrough or feature spec for an unchanged contract. State expected vs actual behavior, failure conditions, severity, and affected scope. Inspect only relevant logs, code, contracts, history, and tests. Identify stack/environment from evidence; do not assume web, database, tenant, or production.
2. **Reproduce narrowly when safe.** Prefer a minimal failing case or test; where impractical, use logs/static traces and mark cause as suspected vs confirmed. Avoid destructive experiments or heavy brute force by default.
3. **Analyze causal chain (systematic, bounded).** Trace the existing project/framework path rather than proposing an unrelated native shortcut. Read the actual failure and recent relevant changes; trace failing inputs/state backward through the relevant layers to the origin. Compare a nearby working case where useful. State one specific hypothesis and evidence that could falsify it; test it with the least costly safe observation. Distinguish confirmed cause from suspected cause. Do not stack speculative patches or repair symptoms while the cause is unknown. If repeated attempts fail or reveal widespread coupling, reassess the architecture rather than continuing trial-and-error; stop and escalate immediately for critical blockers, or report unresolved evidence and limitations otherwise. Use `ns-impact-map` for uncertain shared impact and `ns-risk-review` for serious data/security/operational risk.
4. **Choose planning depth:**
   - `LIGHT`: known localized fix; minimal internal plan, patch, focused verification. No required `spec.md` or `plan.md`.
   - `STANDARD`: cross-component or uncertain regression; a short fix plan with cause/evidence, files or modules, minimal remediation steps, regression test, edge cases, and compatibility check. Keep durable notes if coordination or handoff benefits.
   - `CRITICAL`: credible high-impact risk involving durable data, auth/security, financial behavior, concurrency, externally visible contracts, or production safety (not mere location inside such a module). Record impact, containment, suspected/confirmed root cause, phased fix, verification, deployment/rollback, and monitoring as relevant. Write focused spec for expected behavior **only when requirements or contracts change or remain materially unclear**; otherwise the defect statement and fix plan suffice.
   - If the user requests spec/plan only, prepare it but do not modify product code. If the plan needs a decision without a safe default, parent handles user communication; subagent stops dependent work and escalates to caller.
5. **Protect against regressions.** When safe and meaningful, root-cause confirmation precedes RED reproducer and then GREEN repair; REFACTOR does not waive existing compatibility checks.  Before editing, record intended behavior, relevant existing behavior and affected callers/contracts; note any safe pre-change check and whether it already fails. Preserve existing edits. Add a regression test or repeatable reproduction that exposes the original defect when practical, preferably verified failing before and passing after the fix. Avoid unsafe rollback/reversion just to force a red-green demonstration. For LIGHT, choose the narrowest meaningful safe check. For STANDARD/CRITICAL, check the fix and actually affected prior behavior/contracts; include edge/failure paths only when relevant. For changed public/data contracts, check compatibility; for CRITICAL changes, use isolated staged integration/recovery checks when appropriate.
6. **Fix minimally and verify before claiming completion.** Preserve framework/project mechanisms and existing contracts: do not trade an integration-safe fix for a shorter native bypass. Make the smallest evidence-based change, then run proportionate targeted regression checks and relevant build/static checks. Read outputs and status codes. Classify each failure as introduced, pre-existing, or unknown; do not declare success while an introduced regression remains. If checks cannot safely run, report `NOT_RUN` if not executed, or `BLOCKED` if a required/chosen check is prevented by a specific obstacle, plus residual risk. A successful fix reproduction does not prove unrelated behavior is safe. Do not require an additional check that has no credible regression link.
7. **Check alignment.** Ensure fix plan addresses the demonstrated cause, does not silently change the intended contract, and includes backward compatibility/recovery if relevant. Update existing docs or use the project's conventions; do not create mandatory documents for trivial bugs.
8. **Report** observed issue, root cause/confidence, changed paths or plan artifacts, test results (`PASS`, `FAIL`, `NOT_RUN`, `PRE_EXISTING_FAIL`, `INCONCLUSIVE` where applicable), prior behavior checked, remaining regression risk, and decisions needed (if any). A plausible patch without a reproducer or regression evidence is explicitly unverified.

## Adaptive future-failure gate
Before planning a behavior-impacting change, inspect affected execution paths for realistic latent failure triggers (concurrency, lifecycle/async, retry/timeout, data consistency, queues, scaling, interruption/restart, compatibility, boundary inputs) **only where relevant**. Include material risks in acceptance criteria/plan. After GREEN and any REFACTOR, verify the smallest safe targeted failure-path/recovery cases proportionate to impact; never require a heavy load test or fixed test count. Mark findings `CONFIRMED`, `POTENTIAL`, or `UNVERIFIED`, disclose unrun checks/residual risk, and do not add unrelated changes without authorization. Delegate deeper risk review only for unresolved material risk; preserve project/framework fidelity and read-only/STOP boundaries.
