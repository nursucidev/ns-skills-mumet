# NS New Feature — Adaptive Spec & Plan

## Agent role, STOP, and reporting (self-contained)
- **Role:** parent = main agent serving user; subagent = separately delegated worker, including nested workers. Loading this skill never changes role. A subagent **MUST NOT** ask/contact/notify the user, request approval, or invoke user-facing input tools. Report only to the calling agent, which relays upward.
- **Canonical STOP:** If delegated work cannot safely continue because proceeding risks credible major harm or unauthorized production/destructive/data/secrets/cost effects, or needs a consequential decision with no safe authorized default: **STOP the entire delegated task immediately**, including optional work; report evidence (redact secrets), impact, safe options, decision/permission needed and unfinished work **only to caller**; **END**. Never ask/wait for user. A severe finding during an authorized safely continuing read-only review is not automatically a task blocker; finish the review and use `review_verdict: BLOCK` if warranted. A CRITICAL risk rating alone is not a STOP trigger.
- **Report:** only subagents use compact `task_status`, `result`, `evidence/check_results`, `findings`, `decisions_needed`, `remaining`, plus `review_verdict` for reviews. `task_status` is work progress (`COMPLETED`, `PARTIAL`, `BLOCKED`), separate from check results (`PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `INCONCLUSIVE`, `PRE_EXISTING_FAIL`) and review verdict (`BLOCK`, `FIX`, `NO_FINDINGS`). Parent follows the user's format.

## Ownership
Primary for intentionally new or changed behavior (including spec/plan-only requests). Defects against an unchanged agreed behavior belong to `ns-fix-bug`. For multi-deliverable requests, own only the feature phase; parent coordinates any separate fix/review phase. Supporting `ns-impact-map` and `ns-risk-review` are optional targeted consultations, not required subagent stages.
- **Concurrent implementation:** if delegated among workers, edit only files/state exclusively assigned by the caller; overlapping writers must be serialized or isolated by the parent. Report ownership conflicts instead of racing.

## Adaptive fidelity & minimal-complete-change gate (self-contained)
- Discover the real language(s), framework/toolchain **if any**, architecture, conventions, and affected contracts from the project; never assume a stack. No-framework projects use their established style and idiomatic platform/language mechanisms.
- Preserve established project structure, file roles, supported framework integration/lifecycle, behavior and contracts. Prefer existing project code/patterns, then compatible framework/platform facilities, then installed dependencies, then minimal readable custom code; omit unneeded scope and avoid speculative abstractions/dependencies. **Do not bypass a framework or replace project architecture with native/custom code only for brevity or assumed speed.**
- Native/low-level code remains valid when idiomatic, supported within the project mechanism, or justified by an authorized unmet need. A deliberate architecture/data-format deviation requires authorized scope and proportionate compatibility/regression checks. For performance work, confirm a bottleneck and compare results when practical; optimize within conventions first, preserve safety/correctness, and label unmeasured gains unverified. A delegated worker escalates consequential exceptions only to its caller.

## Adaptive RED–GREEN–REFACTOR for authorized implementation (self-contained)
- This workflow is language/framework neutral and uses project test tools; never requires a new dependency, full suite, worktree, or subagent. `LIGHT`: test-first optional; use the smallest meaningful check. `STANDARD`: for testable behavior prefer RED before implementation, prove it can fail for the expected behavioral reason. `CRITICAL`: use safe isolated risk-proportionate checks, never destructive experiments for RED.
- **RED before implementation:** derive a focused check from acceptance criteria and unchanged behavior, run it against the pre-change baseline, observe the check fail for the expected behavioral reason (not broken test setup). Never manufacture a failing check or disable existing tests.
- **GREEN:** implement the smallest compatible change within project conventions, run the RED check to a genuine PASS, and cover affected prior contracts.
- **REFACTOR only if beneficial:** simplify or improve measured performance without unnecessary redesign; rerun targeted tests and relevant regression checks after material edits. Test evidence is not inferred.
- If meaningful executable RED is unavailable, unsafe, or disproportionate, state why RED is unavailable, use proportionate safe alternative verification and label missing evidence `NOT_RUN` / `BLOCKED` / `INCONCLUSIVE`. For spec/plan-only tasks never edit product code or tests. Performance-only work may use a before/after benchmark without manufacturing a failing test.

## Procedure
1. **Understand before designing.** Apply the adaptive fidelity gate above; preserve established framework/project mechanisms and avoid unnecessary new layers. Inspect the user's request, existing decisions/docs, relevant code, interfaces, tests, project conventions, and actual tool availability. Separate confirmed facts from assumptions. Do not interrogate the user about facts already in the project.
2. **Classify effort by impact, not file count:**
   - `LIGHT`: single-purpose, low-risk, obvious outcome. Use an internal mini-plan if needed; implement and verify directly. No required files, formal brainstorming, or approval.
   - `STANDARD`: several coordinated steps, nontrivial behavior, or shared boundaries. **Always** state testable acceptance criteria and short ordered implementation steps with verification evidence, at minimum in working context. A concise spec/plan file is **optional** unless the user requests it or handoff/complexity warrants persistence; never skip the brief plan merely because no file is written.
   - `CRITICAL`: credible high-impact effects on auth/security, persisted data/migrations, money, externally consumed API/ABI, concurrency, production/destructive operations (not merely a file in those areas). Prepare an explicit spec and phased plan before the affected risky change. Include safety checks, recovery/rollback if relevant. Criticality alone does not mandate asking the user if authorization and decisions are already clear.
   - When the user explicitly asks for `spec`, `plan`, or `plan only`, produce exactly that artifact/scope even for LIGHT; do not silently implement code.
3. **SPEC = what/why, not a code transcript.** Include only applicable headings: `Goal / problem`, `Users and existing context`, `In scope / out of scope`, `Observable behavior and interface/data contracts`, `Acceptance criteria (testable)`, `Important edge/failure cases`, `Constraints and non-functional requirements`, `Assumptions and decisions needed`. Link to existing product/architecture documents rather than duplicating them. For unclear material product decisions, the parent should ask only when no safe default exists; a subagent instead escalates to its caller and stops dependent work.
4. **PLAN = how/check.** Include a suitable RED baseline / GREEN success check / optional REFACTOR recheck for testable behavior, or a justified alternative if RED is not feasible. Prefer the smallest complete design compatible with project conventions; consider actual performance constraints without speculative rewrites. Include the regression protections and verification evidence needed for the affected existing behavior. Based on the actual codebase, list `Scope and approach`, `Affected files or modules (verified, not imagined)`, `Ordered independently verifiable tasks`, `Tests/validation for each meaningful task`, `Compatibility and dependencies`, and `Deployment/rollback when applicable`. Tasks should deliver checkable behavior; merge trivial setup with the task needing it, and split only where a meaningful independent review/test boundary exists. Prefer repo conventions and bounded commands; don't force blanket TDD on untestable work, fresh worker per task, commits, or worktrees.
5. **Plan quality gate (quick):** every acceptance criterion has a task/test, tasks have clear prerequisites and completion evidence, critical risks have controls, and no unnecessary work has crept in. Identify existing behavior that must not change, affected consumers/contracts, and proportionate verification for meaningful affected boundaries; do not invent tests for unaffected boundaries. Update spec/plan if discoveries materially change the approach; don't redo approvals for routine details.
6. **Execute only when requested and authorized.** When a behavior change has a safe meaningful test, follow the adaptive RED–GREEN–REFACTOR gate above; do not claim RED without observing the pre-change failure.  Implement small independently checkable plan slices; preserve existing edits; update the plan only for material discoveries. Consult `ns-impact-map` for uncertain downstream contracts and `ns-risk-review` for material risk, without mandatory delegation.
7. **Regression & evidence gate.** Check that the implementation stays within established structure/integration mechanisms and any authorized exceptions are justified. Apply to code and behavior/delivery-affecting config, dependency, schema, build/CI changes too. Establish the relevant current baseline when safe (including pre-existing failures). For LIGHT, use the narrowest meaningful safe check (inspection may suffice for a purely cosmetic change). For STANDARD/CRITICAL, check new acceptance behavior and genuinely affected existing behavior/contracts; check edge/error paths when relevant. Check contract/compatibility with previous consumers and data, where applicable. LIGHT = targeted, STANDARD = targeted + related regression/contract, CRITICAL = staged safe integration and rollback/recovery checks where relevant. Run only safe tools and check actual exit codes. Distinguish `PASS`, `FAIL`, `NOT_RUN`, `INCONCLUSIVE`, and defensibly `PRE_EXISTING_FAIL`. Do not claim broad regression safety from narrow tests or unrun checks.
8. **Store artifacts only when warranted or requested.** Follow existing repo conventions first. Otherwise a suggested layout is `docs/changes/<topic>/spec.md` and `plan.md` (project-specific alternatives welcome); do not create directories or docs for LIGHT tasks by default. Never overwrite a user's preexisting spec/plan without explicit intent.
9. Report implementation or planning deliverables, paths, acceptance-criteria coverage, test evidence, existing behavior protected, regression gaps, assumptions, risks, and any parent decisions needed. For a plan-only request, report the plan and stop.

## Adaptive future-failure gate
Before planning a behavior-impacting change, inspect affected execution paths for realistic latent failure triggers (concurrency, lifecycle/async, retry/timeout, data consistency, queues, scaling, interruption/restart, compatibility, boundary inputs) **only where relevant**. Include material risks in acceptance criteria/plan. After GREEN and any REFACTOR, verify the smallest safe targeted failure-path/recovery cases proportionate to impact; never require a heavy load test or fixed test count. Mark findings `CONFIRMED`, `POTENTIAL`, or `UNVERIFIED`, disclose unrun checks/residual risk, and do not add unrelated changes without authorization. Delegate deeper risk review only for unresolved material risk; preserve project/framework fidelity and read-only/STOP boundaries.
